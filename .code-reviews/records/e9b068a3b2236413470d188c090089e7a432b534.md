## Summary

Stack: React (Vite, TypeScript, React Router, Redux Toolkit, Tailwind, MSW).

Moves `/todos` out of `AuthLayout` into a new `AppLayout` that gates on the Redux auth
status: it redirects to `/login` (with a "logged out" / "session expired" notice derived from
`endReason` via the new `loginStateAfterSessionEnd`), shows a session-check spinner or a
retry screen while the session is unknown, and renders a header with the user's name and a
logout button. The app now dispatches `bootstrapSession` once at startup (`startSession` in
`main.tsx`). `TodosPage` drops its hand-rolled `/me` fetch, token check and 401 handling and
instead dispatches `fetchTodos` and renders a first `TodoList` (loading / error / items).
`PageLoading` takes an optional label; `messages.home` becomes `messages.session` plus
`messages.todosPage`. Tests updated and added (AppLayout, loginNotice); 407 tests pass and
`tsc -b` is clean.

The refactor is a clear improvement — session gating and 401 handling are now central rather
than per page. One real race is introduced by dispatching `bootstrapSession` at startup while
the login page stays usable during it; plus a missing empty state in the new list.

### Medium (1)
- **src/app/sessionListeners.ts:24** — Startup `bootstrapSession` can overwrite a login that completes while it is still in flight *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed on re-review. `authSlice` now ignores `bootstrapSession.fulfilled` and `bootstrapSession.rejected` once `status` is no longer `"unknown"`, so a login (or session end) that lands first is not overwritten by the late startup answer. `bootstrapSession` remembers the token it sent and only calls `tokenStorage.clear()` on 401 if that token is still the stored one, so the new login's token survives. The global 401 handler in `src/lib/http.ts` (`reportUnauthorized`) already ignores a 401 whose sent token differs from the current one, so the stale `/me` 401 cannot end the new session either. Two new tests in `tests/features/auth/authThunks.test.ts` cover both cases (stale token invalid → new login and token kept; stale token valid for another account → new user kept). Original issue: `startSession` now dispatches `bootstrapSession` on every app start, and `LoginPage` (`src/pages/LoginPage.tsx`) does not wait for or check `auth.status`. If a user with a stale token in storage opens `/login` and submits before `/api/auth/me` answers, `login.fulfilled` sets the new user and token, then the late bootstrap result lands: on 401 the thunk calls `tokenStorage.clear()` (wiping the *new* token) and `bootstrapSession.fulfilled` sets `status: "unauthenticated", user: null`, so `AppLayout` bounces the just-logged-in user back to `/login`. If the stale token is still valid for a different account, `bootstrapSession.fulfilled` instead replaces `user` with the old account while the stored token belongs to the new one. Fix options: ignore `bootstrapSession.fulfilled/rejected` in `authSlice` once status is no longer `"unknown"` (and only clear the token in the thunk if it is still the token that was sent), or have `LoginPage`/`AuthLayout` wait while status is `"unknown"`. Narrow timing window, hence Medium rather than High.
