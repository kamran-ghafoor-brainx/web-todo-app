## Summary

Stack: React (Vite, TypeScript, Redux Toolkit, React Redux, React Router).

Scope: all changes (option b). Everything was already staged, and the working tree had no unstaged or untracked changes.

This diff adds the auth session logic to the Redux store:
- `sessionEnded` now carries a `reason` (`"loggedOut" | "expired"`), and the auth slice records it as `endReason`.
- New `bootstrapSession`, `login` and `logout` thunks in `authThunks.ts`. The auth slice handles `bootstrapSession.*` and `login.fulfilled`.
- New plain selectors in `authSelectors.ts`, exported from the feature's `index.ts`.
- `registerSessionListeners` connects the `http` 401 handler to the store: it clears the token and dispatches `sessionEnded({ reason: "expired" })`. `main.tsx` calls it before rendering.
- `LoginPage` now dispatches `login(...).unwrap()`, and `TodosPage` logout dispatches the `logout` thunk.
- Tests: a shared `tests/utils/renderApp.tsx` that wraps the app in a fresh store, and new tests for the thunks and the session listeners. Existing store tests are updated for the new payload.

Verification: `tsc -b` and `eslint` both pass with no output, and `vitest run` passes 281/281.

Checked and found correct: when `sessionEnded` fires, the root reset runs first and then the slice sets `status` and `endReason`. Logout ends with `endReason: "loggedOut"` even if `/auth/logout` returns 401, because the handler's `"expired"` event is dispatched first and the thunk's `"loggedOut"` event comes after it. `login` uses `auth: false`, so a wrong-password 401 does not trigger the session handler. The `authSlice` → `authThunks` → `createAppAsyncThunk` → `store` chain is type-only at the `store` step, so there is no runtime import cycle.

  - ai_reasoning: There are now two sources of truth for one session. After `login.fulfilled` puts the user in the store, `TodosPage` ignores it and fetches `/auth/me` again. ### Low (2)
- **src/features/auth/authThunks.ts:28** — The `bootstrapSession` `condition` only checks `status === "unknown"`, so it does not block a second dispatch while the first is still in flight. *(correctness)*
  - status: skipped
  - dev_reasoning: bootstrapSession will be dispatched exactly once from main.tsx in A3, outside React, so StrictMode cannot double it. The only other caller is the Retry button, which is shown only after the first run has rejected (nothing in flight).

Both results write the same state, so there is no wrong outcome, only a duplicate request. That defeats the purpose of the guard. Fix: track a pending flag (for example a `bootstrapPending` field, or a status like `"checking"`) and check it in `condition`.
