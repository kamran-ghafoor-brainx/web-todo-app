## Summary

Stack: React (Vite, TypeScript, Redux Toolkit 2, React Redux 9, React Router 8).

Scope: all changes (option b). Everything was already staged, and the working tree had no unstaged or untracked changes.

This diff adds the Redux foundation for the auth frontend (Phase 2.2):
- a `configureStore` store built by `makeStore(preloadedState)`, with a root reducer wrapped in `withSessionReset`. On the `app/sessionEnded` action that wrapper resets every slice to its initial state.
- typed `useAppDispatch` / `useAppSelector` hooks and a typed `createAppAsyncThunk` with a `string` reject value.
- an `auth` slice with no case reducers yet. Its only extra reducer sets `status` to `"unauthenticated"` on `sessionEnded`. Its state is `status: "unknown" | "authenticated" | "unauthenticated"`, `user`, and `bootstrapError`.
- a `Providers` component that wraps `StrictMode` and the Redux `Provider`. `main.tsx` now uses it.
- `renderWithProviders` now builds a fresh store per test (or accepts one) and returns `store` and a `userEvent` instance.
- `tests/app/store.test.ts` covers the reset behaviour.

Verification: `tsc -b` and `eslint` both pass with no output. `vitest run` passed 268/268 on three back-to-back runs. One earlier run had 1 failure, in a test file outside this diff. That looks like a timing-dependent flaky test that already existed, so it is not counted against this change.

Nothing dispatches `sessionEnded` and nothing reads the auth slice yet. The 401 handler and cross-tab wiring are still deferred, as recorded in the skipped "session-aware routing" finding of commit fe066c3.

### Medium (1)
- **src/features/auth/authSlice.ts:18** — When the session ends, the reset puts `auth.status` back to `"unknown"` instead of `"unauthenticated"`. After a logout, a 401, or a logout in another tab, the app therefore reads the session as "not yet determined" when it is actually known to be over. `tests/app/store.test.ts:21` asserts and locks in this behaviour. *(correctness/state)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed on re-review. `authSlice` now has `extraReducers` with `builder.addCase(sessionEnded, (state) => { state.status = "unauthenticated"; })` (authSlice.ts:23-28). `withSessionReset` still passes `undefined` state, so this case runs on the fresh initial state: `user` and `bootstrapError` are cleared and `status` becomes `"unauthenticated"`. The test at `tests/app/store.test.ts:21-29` now expects `{ ...initialAuthState, status: "unauthenticated" }`. The generic all-slices reset test is unchanged and still passes. `tsc -b`, `eslint`, and `vitest run` (268/268) all pass. Original reasoning follows. `withSessionReset` calls the reducer with `state = undefined`, so `authSlice` returns `initialAuthState`, which has `status: "unknown"`. In this design `"unknown"` is the bootstrap state before `/auth/me` has answered. Route guards (Phase 4.5) usually render a loading screen for `"unknown"` and redirect only on `"unauthenticated"`. After logout, or a cross-tab logout, the user would then sit on a spinner, or bootstrap would run again with no token, instead of being sent to `/login`. The fix fits the existing design: add `extraReducers: (b) => b.addCase(sessionEnded, (state) => { state.status = "unauthenticated"; })` to `authSlice`. The reset passes `undefined` state together with the `sessionEnded` action, so this case runs on the fresh initial state and every other slice still resets. Then change the first test to expect `{ ...initialAuthState, status: "unauthenticated" }`. This is Medium rather than High because nothing consumes the slice yet.

### Low (1)
- **tests/utils/renderWithProviders.tsx:17** — If a test passes both `store` and `preloadedState`, `preloadedState` is silently ignored, because it is only used in the default value of `store`. *(maintainability/test-utils)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed on re-review. `Options` is now a discriminated union, `{ preloadedState?: Partial<RootState>; store?: never } | { store: AppStore; preloadedState?: never }` (renderWithProviders.tsx:8-14), so passing both options is a type error. The store is now built in the function body (`options.store ?? makeStore(options.preloadedState)`, line 18), not in a destructuring default. `tsc -b` passes. Original reasoning follows. A test that writes `renderWithProviders(ui, { store, preloadedState: {...} })` gets the store's existing state, not the state it asked for. The resulting failure points away from the real cause. Make the two options mutually exclusive in the `Options` type (`{ store: AppStore; preloadedState?: never } | { store?: never; preloadedState?: Partial<RootState> }`), or throw when both are given. This has no production impact.
