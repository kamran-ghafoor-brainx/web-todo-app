This diff adds shared UI building blocks:
- `Dialog`: a modal built on the native `<dialog>` / `showModal()`. The parent opens it by mounting it and closes it by unmounting it. Escape (`cancel`) is prevented and passed to `onClose`. A native `close` is also passed to `onClose`. Focus goes back to the opener on unmount.
- `ConfirmDialog`: built on `Dialog`. Focus starts on Cancel, and while `loading` both buttons are disabled and Escape is ignored.
- A toast system: `ToastProvider` (an always-mounted polite live region, a 5 s auto-dismiss, at most 3 toasts), `toastContext` and `useToast`, wired into `Providers` and both test render helpers.

### Medium (2)
- **src/components/Dialog.tsx:56** — If the browser closes the dialog and the parent does not unmount it, the DOM and React state get out of sync. The dialog stays closed and cannot be reopened. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `handleClose` (Dialog.tsx:58-63) now calls `onCloseRef.current()` and then queues a microtask that runs `showModal()` again if the effect is still active and the dialog is closed. `close` is a discrete event, so a parent `setState` in `onClose` schedules React's sync flush microtask before this one. If the parent unmounts the dialog, the cleanup runs first and sets `active = false`, so nothing reopens. If the parent keeps it mounted (for example, `ConfirmDialog` while `loading`), the dialog opens again. Two new tests cover this: "follows the browser when it closes the dialog by itself" and "reopens if the browser force-closes it while the action runs". Previous analysis: Chromium's close-watcher anti-abuse rule makes `cancel` non-cancelable on a second Escape when there was no user activation in between, so the dialog closes natively anyway. `handleClose` then calls `onClose`. `ConfirmDialog` ignores that call while `loading`, so the confirm stays mounted with `<dialog>` closed and invisible. If the action fails and the parent keeps the dialog open (for example to allow a retry), the user sees nothing. Clicking the trigger again sets `open` to `true` when it is already `true`, so the effect never runs `showModal()` again and the dialog is stuck. For a plain `Dialog` whose `onClose` does nothing (e.g. while saving), the same thing happens. Fix: in `handleClose`, after calling `onCloseRef.current()`, check whether the dialog is still mounted once React has had a chance to commit. For example, `queueMicrotask`/`requestAnimationFrame(() => { if (dialog.isConnected && !dialog.open) dialog.showModal(); })`. Alternatively, have the parent's veto reopen the dialog. Add a test that fires `close` on a `ConfirmDialog` with `loading` set.
- **src/components/toast/ToastProvider.tsx:43** — While any `Dialog` is open, toasts are hidden behind it and are not announced. *(accessibility)*
  - status: skipped
  - dev_reasoning: Handled by a usage rule rather than code, documented on useToast: never toast while a modal Dialog is open. The top layer makes everything outside the modal inert, and portalling toasts into dialogs would couple Dialog to the toast system. Planned call sites follow it: EditTodoDialog (E2) shows save errors inline in the form, and the delete ConfirmDialog (E4) closes before the success or failure toast.
  - ai_reasoning: `showModal()` puts the dialog in the top layer and makes the rest of the document inert. The toast region is a normal `fixed z-50` element under `<body>`, so it is drawn under the `::backdrop` (no z-index can beat the top layer). It is also removed from the accessibility tree, so its `aria-live` additions are not announced, and its dismiss button cannot be clicked or focused. `ConfirmDialog` has a `loading` state so an async action can run while it is open. The natural failure path, `toast.error("Couldn't delete")` with the dialog still open (or closing in the same tick), will therefore often go unseen and unheard. Fix: render the toast region in the top layer too, for example as a `popover="manual"` element that you `showPopover()` again after a dialog opens. Or show errors inside the dialog and only toast after it unmounts, and document that rule on `useToast`.

### Low (1)
- **src/components/toast/ToastProvider.tsx:65** — Toasts, error toasts included, always close after 5 s. The timer does not pause on hover or focus, so a toast can disappear while its own dismiss button has keyboard focus. *(accessibility)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. Each `ToastItem` (ToastProvider.tsx:61-77) tracks `hovered` and `focused`. The timer effect stops while either is true and keeps the remaining time in `remainingMs`, so the toast cannot disappear while it is hovered or while its dismiss button has keyboard focus. Two new tests cover this: "pauses while hovered, then finishes the remaining time" and "stays while its dismiss button has keyboard focus". Keeping error toasts until dismissed was optional and was not done. With the pause, this is acceptable. Previous analysis: The timer keeps running when the pointer is over the toast or focus is inside it. A keyboard user who tabs to "Dismiss notification" can have the `<li>` unmount under them, and focus then drops to `<body>`. A fixed 5 s timeout with no way to extend it also falls short of WCAG 2.2.1 (Timing Adjustable) for error messages that users need to read. Fix: pause the timer on `onMouseEnter`/`onFocus` and resume it on `onMouseLeave`/`onBlur` (track the remaining time). Optionally, keep `error` toasts until they are dismissed.
