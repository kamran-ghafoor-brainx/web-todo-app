## Summary

Adds the todos state layer: `todosApi` (all five endpoints over the shared `http` client), the `todos` slice registered in the root reducer (so it resets on `sessionEnded`), async thunks for fetch/create/update/delete with 404 → "already gone" handling, selectors (`selectTodoCounts` memoised), URL-driven filtering (`useFilteredTodos`), date helpers (`toDateOnly` moved out of the mock seed and reused there), and a feature barrel. The slice ignores answers from requests started before a session reset via `activeRequestIds`, and blocks a second concurrent mutation on the same item via `pendingById`.

Stack: React (Redux Toolkit, React Router). Typecheck, ESLint and the 133 todos/mocks tests all pass.

### Medium (1)
- **src/features/todos/todosSlice.ts:50** — `fetchTodos.fulfilled` replaces `items` with the server list wholesale, so a create/update/delete that settled while the fetch was still in flight is lost from the UI. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `fetchTodos.pending` now opens a `changesDuringFetch` log, and every confirmed create/update/delete (and 404 "already gone" removal) goes through `commit()`, which applies the change to `items` and records it in the log. `fetchTodos.fulfilled` replays the log over the server list via `applyChange` (`created` won't duplicate a todo the snapshot already has; `removed`/`updated` are idempotent), then clears it; `rejected` clears it too. Session reset drops the log along with everything else. New slice tests cover create during a stale fetch, and delete + update during a stale fetch, and check that the log is cleared. 136 todos/mocks tests pass.
  - previous ai_reasoning: Fetch and mutation thunks can run at the same time (the fetch condition only blocks a second fetch). Scenario: the list is loading (first load, or a retry/refresh), the user creates a todo; the server answers the GET from a snapshot taken before the POST, the POST answers first and `createTodo.fulfilled` unshifts the item, then `fetchTodos.fulfilled` overwrites `items` and the new todo disappears until the next reload. The same applies to a delete (the item comes back) or an update (old values come back). Fix options: skip mutations while `status === "loading"`, or when the fetch settles, reapply mutations that finished after the fetch started (e.g. record the fetch's requestId and keep a list of ids created/deleted since then), or refetch after a mutation lands during a load. Add a slice test for the create-during-fetch ordering.
